1. Project Overview
Objective. Build a multi-agent application that accepts a clinical question or de-identified case summary, retrieves relevant
evidence from approved references, checks evidence quality, and prepares a structured summary for a qualified healthcare
professional to review.
Safety boundary. This is an educational decision-support prototype, not an autonomous diagnostic, prescribing, triage, or
treatment system. It must not make final clinical decisions or present generated content as a substitute for a clinician.
Core use cases
 Retrieve and summarize approved clinical guidelines and biomedical literature.
 Summarize supplied patient-record facts while separating documented facts from missing or inferred information.
 Attach references to material claims and flag evidence conflicts or insufficient support.
 Route uncertain, conflicting, urgent, or out-of-scope cases to human review.
 Log agent actions, retrieval sources, validation results, and failure reasons.
Success criteria
 Substantive evidence claims are traceable to retrieved sources or marked unsupported.
 The system does not invent patient history, medication data, citations, or eligibility conclusions.
 Missing data and uncertainty are visible in the output.
 Tool failures and source conflicts fail safely or trigger review.
 Evaluation is repeatable on a fixed, versioned test set.
2. Reference Architecture

↓

■■■ Evidence Retrieval Agent (approved sources)

■■■ Safety & Policy Agent (scope, missing data, escalation)
■■■ Summary Agent (draft with citations)
↓
Output Validator → Human Review Queue → Audit Log
Workflow design
Use sequential steps for intake, retrieval, verification and drafting; conditional routing for incomplete or conflicting cases;
parallel search for independent approved sources; bounded retries for transient failures; and allowlisted tools. Keep write
actions disabled by default and require human approval for any change to a clinical record.

6. Data and Knowledge Sources
Start with a small, versioned, legally usable collection. Use synthetic or properly de-identified cases during development.
 Guidelines: approved documents with publisher, version, effective date and section metadata.
 Research: permitted biomedical literature; preserve PMID/DOI and publication date.
 Patient context: synthetic FHIR resources or de-identified records with provenance for each extracted fact.
 Terminology: approved coding, medication and clinical terminology references where licensing permits.
 Document registry: source ID, title, organization, version, retrieval date, review status and superseded status.
Do not ingest arbitrary internet pages into a clinical knowledge base without source review, licensing checks, versioning,
and a process for removing outdated guidance.
7. Sample Input and Expected Output
Sample request: “Prepare an evidence summary for clinician review about a patient with a documented history of asthma who
reports worsening cough. Summarize relevant information from the supplied record and approved guidance. Do not diagnose
or recommend medication changes.”
Facts supplied: adult patient; asthma is listed in the provided record; worsening cough is reported; current medication list and
vital signs were not supplied.
Example structured output
 { "case_status": "human_review_required", "record_facts": [ "Asthma is documented in the supplied
record", "Worsening cough is reported" ], "missing_information": [ "Current medication list", "Vital
signs", "Symptom duration and associated symptoms" ], "evidence_summary": [ { "claim": "Summary grounded
in retrieved approved source", "source_id": "GUIDE-001", "section": "Section identifier" } ],
"limitations": [ "Not a diagnosis or treatment plan", "Source version requires review" ],
"escalation_reason": "Clinical assessment required; context incomplete" }
GUIDE-001 is an illustrative placeholder and must be replaced by a real retrieved source. The example does not invent vital signs, infer severity, or
recommend medication.

9. Evaluation Plan
 Dimension
Example metric / test
Retrieval quality
Recall@K, Precision@K, MRR and NDCG on expert-labelled queries.
Evidence grounding
Percentage of material claims supported by cited passages; unsupported-claim rate.
Citation quality
Citation correctness, source existence, passage support and source-date validity.
Safety boundary
Rate of prohibited diagnosis/treatment outputs; correct abstention/escalation rate.
Extraction quality
Precision, recall and F1 for selected clinical entities and fields.
Reliability
Task completion, tool failure, schema-valid output, loop rate.
Efficiency
P50/P95 latency, tokens per case, cost per completed case.
Robustness
Missing fields, contradictory sources, adversarial documents, malformed inputs, tool outages.
Automated metrics alone cannot establish clinical safety. Any workflow that could influence care requires qualified clinical
review and a formal validation process.

11. Implementation Roadmap
 Phase
Deliverable
1. Scope & governance
Define intended/prohibited use, sources, data handling, reviewer roles and acceptance criteria.
2. Baseline retrieval
Parse/version documents; build sparse+dense retrieval; evaluate retrieval independently.
3. Single-agent baseline
Generate structured evidence summaries with citations and abstention.
4. Multi-agent workflow
Add narrow agent roles, explicit state transitions, tool allowlists and bounded retries.
5. Safety & validation
Add schema checks, citation verification, missing-data handling, escalation and audit traces.
6. Evaluation & UI
Run fixed test suite; expose evidence and reviewer actions in Streamlit.
7. Readiness review
Threat model, privacy review, load/failure tests, monitoring and rollback plan.

Definition of done
A reviewer can submit a synthetic case, inspect retrieved evidence and citations, distinguish documented from missing
facts, see safety/validation outcomes, and trace the final status in logs—without the system making an autonomous clinical
decision.
